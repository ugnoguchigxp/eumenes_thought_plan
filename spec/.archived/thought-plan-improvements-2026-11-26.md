## 3. 改善案

### 3.1 測定を繰り返し実行にし、プランの版ごとに合格率を出す

| 項目 | 内容 |
| --- | --- |
| 問題 | 1周1標本で、最初の不合格で止まる（`examples/run.ts:182-185`）。合格率が出ない。報告はプランの版を持たず、15件の報告は版1〜3が混ざっている |
| 変更 | `examples/run.ts` に測定の実行を足す。既定の動き（1回ずつ・最初の不合格で止まる）は調整用として残す |
| 検証 | 固定試験: fixture で `--repeat 3` を回し、シナリオごとの合格数・プランの digest・不合格のチェック名が報告に入ること |
| 合格条件（実モデル） | チューニング用の推論ありシナリオ9件それぞれ30回中27回以上。全体で95%以上 |
| 費用の見積もり | 9件×30回×約2回の推論＝約540回、約0.10ドル。4並列で約10分 |

```sh
bun run examples -- --repeat 30 --concurrency 4
```

```json
{
  "mode": "live",
  "model": { "model": "<config/llm.json の値>", "effort": "low" },
  "scenarios": [
    {
      "id": "live2d-goal-stalled",
      "set": "tuning",
      "plan": { "id": "review-judge-plan", "version": 3, "digest": "…" },
      "runs": 30,
      "passed": 29,
      "failedChecks": { "選んだ方法の最初の手が登録検査": 1 },
      "failedRunIds": ["…"],
      "modelCalls": 60,
      "tokens": { "input": 39270, "output": 14355 }
    }
  ],
  "spend": { "calls": 540, "spentUsd": 0.1 }
}
```

| 規則 | 内容 |
| --- | --- |
| `--repeat N` | 各シナリオを N 回実行する。不合格でも止めない。指定しなければ現行どおり |
| 推論0回のシナリオ | 1回だけ実行し、合格率の集計から外す（`modelCalls: 0` と表示） |
| 実行の記録 | 台帳の実行に、シナリオID・推論強度を `context`（§3.9の列）で残す |
| 設計書§10 | 測定の表を「プランの版・シナリオ・回数・合格数」に置き換える |

### 3.2 取り置きのシナリオを足し、チューニング用と分ける

| 項目 | 内容 |
| --- | --- |
| 問題 | プランの指示文は、測定と同じ10件を見て直した。別の状況で同じ結果が出るかは未測定 |
| 変更 | `examples/scenarios/heldout.ts` に12件を足す。`Scenario` に `set: "tuning" \| "heldout"` を足す。既定の実行はチューニング用だけ。`--set heldout` で取り置きを回す |
| 検証 | 固定試験: 12件が fixture の応答で合格する（既存の `test/examples.test.ts` と同じ形） |
| 合格条件（実モデル） | 取り置きの各シナリオ30回中24回以上、全体で90%以上。約720回の推論、約0.14ドル |

| プラン | 取り置きのシナリオ（題材は Live2D・git 以外にする） | 見ること |
| --- | --- | --- |
| `review-judge-plan` | 原因の違う失敗が2回、許可が変わった | 続ける。失敗した能力と別の能力を最初の手にする |
| `review-judge-plan` | 提示した能力をすべて試し、同じ外部要因で失敗 | 待つ。待つ対象と見直す時期がある |

### 3.3 緩めたチェックを戻し、振り返りのプランに「変えられるもの」の入力を足す

| 項目 | 内容 |
| --- | --- |
| 問題 | `live2d-goal-reflection` のチェックは実質 `avoid` の件数しか見ていない（`examples/scenarios/live2d-goal.ts:246-252`）。実モデル11回中8回は「入力を12,000未満に絞れば同じ方法でよい」と答えた。実際の停止では、監督の判断入力の長さは依頼側から変えられなかった。プランの入力に「依頼側が変えられるもの」がないので、モデルはそれを知りようがない |
| 変更 | `post-failure-reflection` 版2。入力に `controls`（依頼側が次の試行で変えられるもの）を足し、`change` の段の出力で、変える条件を `controls` の中から指すようにする |
| 検証 | 固定試験: 版2が読み込める。`controls` が空なら `sameApproachAllowed` は false だけが整合する（§3.6の規則。§3.6を採らない場合はシナリオのチェックで見る） |
| 合格条件（実モデル） | `live2d-goal-reflection` で `controls` に監督の入力長を含めない入力を渡し、30回中27回以上で `sameApproachAllowed: false`、または変える条件が `controls` の中にある |

| --- | --- |

### 3.4 条件の値を読込み時にスキーマと照合する

| 項目 | 内容 |
| --- | --- |
| 問題 | `runWhen`・`skipWhen` の `equals`・`in` の値は照合されない（`src/conditions.ts:27-43`、`src/plan.ts:216-222`）。値を書き間違えると、段が黙って常に省かれる（または常に動く）。「考えずに進む」事故が読込みを通る |
| 変更 | 条件の参照先のスキーマが `enum`・`const`・`boolean`・数値・文字列のいずれかに決まるとき、値がそのスキーマで取り得ない場合は `PlanError("condition_value_unreachable")` にする。`anyOf` と開いたオブジェクトの先は照合しない（現行の参照の検査と同じ範囲） |
| 検証 | 固定試験: `{"path":"$.stages.judge.output.decision","equals":"gone"}`（enum は `go`・`stop`）を拒否する。`in` は1件でも取り得ない値があれば拒否する。boolean の参照に文字列 `"true"` を拒否する。同梱4件と `code-triage` は通る |

### 3.5 失敗の種類を返し、実行を `running` のまま残さない

| 項目 | 内容 |
| --- | --- |
| 問題 | 利用側は「通信が失敗して考えられなかった」と「考えた結果が使えなかった」を区別できない。前者は同じ入力でもう一度呼ぶ意味があり、後者は同じ入力でもう一度呼ぶのが「考えない繰り返し」になる。また、台帳の書込みが途中で失敗すると実行の行が `running` のまま残る |
| 変更 | 下の3点 |
| 検証 | 固定試験: `retryable: true` を持つエラーを投げる口で `RunResult.failure.retryable` が true。持たないエラーは false。台帳の2回目の書込みを失敗させると、throw したうえで実行の行が `failed`・`ledger_write_failed` になる。`running` の実行を期限で閉じる関数が、期限より新しい実行に触れない |

| 変更点 | 内容 |
| --- | --- |
| `RunResult.failure` | `{ stageId, code, retryable } \| null` を足す。`retryable` は、口が投げたエラーの `retryable === true` のときだけ true。実行器自身の失敗（`stage_output_invalid` など）は false。実行器は再試行しない（設計書§4.1のまま） |
| 途中の台帳の失敗 | 段の記録か終了の記録が失敗したら、実行を `failed`・`ledger_write_failed` で閉じる書込みを1回だけ試み、元のエラーを throw する |
| 放置された実行 | `abandonRunsInTransaction(db, { startedBeforeMs, mode? })` を公開する。`running` の実行を `failed`・`run_abandoned` にする。MCP サーバーは起動時に、24時間より古い `stepwise` の `running` を閉じる。ホストは起動時の回復処理から呼ぶ |

失敗の種類の表（`standalone/openai.ts` の場合）:

| コード | `retryable` | 意味 |
| --- | --- | --- |
| `llm_connection`、`llm_api_429`、`llm_api_5xx` | true | 考えていない。入力が同じでも呼び直してよい |
| `llm_max_tokens`、`llm_refusal`、`llm_incomplete`、`llm_output_not_json`、`llm_output_schema`、`stage_output_invalid`、`stage_output_inconsistent` | false | 考えた結果が使えない。同じ入力で呼び直さない |
| `stage_input_too_large`（§3.8） | false | 入力を減らすまで呼ばない |
| `llm_spend_limit`、`llm_api_key_missing`、`llm_price_missing`、`llm_model_not_confirmed` | false | 設定の問題 |

`retryable` は台帳の段の行にも残す（§3.9の migration の列）。

### 3.6 出力の整合の規則（`ensure`）を段に書けるようにする

| 項目 | 内容 |
| --- | --- |
| 問題 | JSON Schema では表せない整合を、実行器は検査しない。モデルが選んだ参照（`capabilityRef`、`chosen` の添字、`optionId`）が入力にあるか、判断と付随項目が対応するかは、シナリオのチェックだけが見ている。実測では `keepPlan: true` かつ `planRemaining: false` が23回中2回。参照が提示外だった例は0/12だが、ホストはこの値でそのまま能力を引く |
| 変更 | 段に任意のキー `ensure`（規則の配列）を足す。出力がスキーマを通った後に、推論なしで評価する。1件でも満たさなければ、ライブラリでは段を `failed`・`stage_output_inconsistent` にして止める。段ごとの実行では提出を受け付けず、満たさなかった規則を返す（エージェントは直して出し直せる） |
| 検証 | 固定試験: 下の3つの形それぞれで、満たす出力は通り、満たさない出力は `stage_output_inconsistent`。規則の参照先がスキーマにない場合は読込みで拒否。段ごとの実行では不合格の提出が `rejected` として記録され、段が進まない。同梱プランの版を上げ、§1.2の照合を試験として固定する |
| 合格条件（実モデル） | §3.1・§3.2の測定で、`stage_output_inconsistent` による失敗が全実行の2%以下 |

規則の形は3つだけにする。

| 形 | 意味 |
| --- | --- |
| `{ "when": 条件, "then": 条件 }` | `when` が成り立つなら `then` も成り立つ。条件は既存の形（`equals`・`in`・`exists`・`all`・`any`・`not`）。参照に `$.output…`（その段の出力）を使える |
| `{ "each": 参照, "in": 参照 }` | 左の値がすべて、右の値の集まりに含まれる。この2つの参照だけ `[*]`（配列の全要素）を使える |
| `{ "index": 参照, "within": 参照 }` | 左の整数が、右の配列の添字として有効 |

`review-judge-plan` 版4の例:

```json
"ensure": [
  { "when": { "path": "$.output.decision", "equals": "wait" }, "then": { "path": "$.output.wait", "exists": true } },
  { "when": { "path": "$.output.decision", "equals": "ask" }, "then": { "path": "$.output.question", "exists": true } },
  { "when": { "path": "$.output.keepPlan", "equals": true }, "then": { "path": "$.inputs.history.planRemaining", "equals": true } }
]
```

```json
"ensure": [
  { "index": "$.output.chosen", "within": "$.output.candidates" },
  { "each": "$.output.candidates[*].steps[*].capabilityRef", "in": "$.inputs.capabilities[*].ref" }
]
```

| 同梱プラン | 足す規則 |
| --- | --- |
| `review-judge-plan` | 上の5件 |
| `impact-decision` | `estimates[*].optionId` が `options[*].id` に含まれる。`chosen` が null でなければ `options[*].id` に含まれる。`needsConfirmation` が true なら `chosen` は null で `confirm` がある。false なら `chosen` がある |
| `post-failure-reflection`（§3.3の版2） | `sameApproachAllowed` が true なら `change` がある。`change.controlId` が `controls[*].id` に含まれる |

表せないもの: 「選んだ選択肢の見積もりの影響が、許された範囲に入っている」は、配列から1件を引く照合が要るので、この3つの形では書けない。これは従来どおり利用側が見る（本家の再設計書§3.3「影響の採否はホストが決める」と同じ分担）。

モデルに渡すスキーマは変えない（提示した参照を enum として実行ごとに埋め込むことはしない）。提示外の参照は実測0件で、実行ごとにスキーマが変わると入力キャッシュの先頭が揃わなくなる。

### 3.7 失敗した段の出力と使用量を記録する

| 項目 | 内容 |
| --- | --- |
| 問題 | 「すべての入力・出力を記録」に対し、失敗した段は入力しか残らない（`src/run.ts:220-228`）。不適合だった本文と、その呼出しで使ったトークン数が消える（`standalone/openai.ts:176-207` は使用量を費用の計には入れるが、エラーには載せない）。失敗の原因を台帳から調べられない |
| 変更 | 口が投げるエラーに、任意で `usage`（入力・出力・キャッシュのトークン数）、`model`、`raw`（受け取った本文）を載せられるようにし、実行器は失敗した段の行にそれを記録する。`standalone/openai.ts` の `LlmCallError` に載せる。実行器が自分で不適合と判断した場合（`stage_output_invalid`・`stage_output_inconsistent`）は、受け取った値と使用量を記録する。台帳が `off` なら何も残さない |
| 検証 | 固定試験: スキーマに合わない値を返す口で、段の行の `output_json` にその値、`input_tokens`・`output_tokens` に口の値が入る。`raw` を載せたエラーで `output_json` に入る。`RunResult` と MCP の返り値には不適合の本文を載せない（台帳だけ） |

### 3.8 段の入力の大きさに上限を置く

| 項目 | 内容 |
| --- | --- |
| 問題 | 段の入力は配線した値をそのまま JSON にする（`src/run.ts:74-77,197`）。試行が増えれば入力は線形に増える（実測: 試行8件・能力3件で1,590トークン）。上限がないので、超えたときは提供側のエラーか、長い入力での品質低下として現れる。今回の実際の停止の直接の原因は、監督の判断入力の上限超過だった |
| 変更 | 段の入力の JSON が上限を超えたら、推論を呼ばずに段を `failed`・`stage_input_too_large` にする。既定は48,000字（`PLAN_LIMITS.stageInputCharacters`）。段に任意の `maxInputCharacters`（1〜256,000）を書ける。段ごとの実行では `start`・`submit` が同じコードで実行を `failed` にして返す |
| 検証 | 固定試験: 上限を超える入力で推論0回、段は `failed`、コードは `stage_input_too_large`、台帳には入力の字数だけを残し本文は残さない。上限ちょうどは通る |

入力を減らす（古い試行をまとめる）のは利用側の仕事にする。実行器は切り詰めない。

### 3.9 同じ入力なら前回の結論を使い、推論を呼ばない

| 項目 | 内容 |
| --- | --- |
| 問題 | 「思考は省けるなら省きたい」に対し、いま省けるのはプランの条件に書いた場合だけ。入力が前回とまったく同じでも、呼べば同じ段をもう一度推論する。本家の再設計書§3.3「同じ入力の再思考」は、これをホストが自前で作る前提になっている |
| 変更 | 台帳の実行に入力の digest を記録し、`runPlan` に `reuse: "same_inputs"`（既定は無効）を足す。有効で、同じ `subjectRef`・同じプランの digest の直近の実行が `completed` かつ入力の digest が同じなら、推論を呼ばずにその出力を返す。新しい実行の行を1件残し、どの実行の結論を使ったかを記録する。直近の実行が `failed`・`cancelled` の場合は使わない（その扱いは§3.5の `retryable` を見て利用側が決める） |
| 検証 | 固定試験: 同じ入力で2回呼ぶと2回目は推論0回、`RunResult.reusedRunId` が1回目の実行ID、出力が等しい。入力が1字違えば推論する。プランの本文が変われば推論する。`subjectRef` がない、または台帳が `off` なら常に推論する。間に別の入力の実行が入れば使わない |

新しい migration（適用済みの `0001` は変えない）:

```sql
ALTER TABLE thought_plan_runs ADD COLUMN inputs_digest TEXT;
ALTER TABLE thought_plan_runs ADD COLUMN reused_run_id TEXT;
ALTER TABLE thought_plan_runs ADD COLUMN context_json TEXT;
ALTER TABLE thought_plan_stages ADD COLUMN retryable INTEGER;
CREATE INDEX thought_plan_runs_latest ON thought_plan_runs (subject_ref, plan_digest, started_at_ms) WHERE subject_ref IS NOT NULL;
```

| 列 | 使い道 |
| --- | --- |
| `inputs_digest` | 入力の正準 JSON の SHA-256。既存の行は null で、再利用の対象にならない |
| `reused_run_id` | 結論を使った元の実行 |
| `context_json` | 利用側が実行に付ける任意の情報（`RunOptions.context`）。測定ではシナリオIDと推論強度、本家では1周の起点と目標の版を入れる。推論には渡さない |
| `retryable` | §3.5 |

## 4. 見送るもの

| 案 | 見送る理由 |
| --- | --- |
| 入力キャッシュを効かせるために system context を1,024トークン以上に伸ばす | 費用の大半は出力側（1周あたり入力約0.001ドル、出力約0.003ドル）。効くのは入力の一部だけで、長い指示文は結果を変える |
| 実行器が不適合の出力を自分で出し直させる | 設計書§4.1の方針（再試行は利用側）。実測でスキーマ不適合は0/173。§3.6の規則で不合格が出ても、まず数を測る（合格条件2%） |
| 条件に大小比較・件数・配列の検索を足す | いまの同梱プランは、ホストが渡す真偽値（`planRemaining`・`changed`）で足りている。必要になった具体例が出てから足す |
| プランの中の繰り返し | 設計書§1の方針のまま |
| MCP の呼び出し元ごとの隔離、MCP のサンプリング | 一人で使うローカルの道具という設計書§6の前提のまま |
| ホストの DB で `secure_delete` を設定する | 接続の設定はホストの持ち物。単独の台帳では設定済み（`src/ledger.ts:363`） |
| 提示した参照を、実行ごとに出力スキーマの enum として埋め込む | §3.6 に書いたとおり。提示外の参照が実測で出たら再検討する |
